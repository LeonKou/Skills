# 已确认工程规范

本文件只记录已确认的强制要求。

## API
- REST API 路径（微服务网关架构）使用 `api/{service}/{module}/v1/{controller}/{action}`；路径全小写、单词用 `-`、无尾斜杠、版本使用正整数；内部接口使用 `api/inner/...`。
- HTTP 语义必须一致：GET 查询、POST 创建/批量/复杂动作/上传、PUT 完整替换、PATCH 部分更新、DELETE 删除。
- 禁止 path 参数。业务公共参数优先放 query；安全类参数放请求头；请求头不得承载业务逻辑数据；认证 Token 放 Authorization 等认证头；query 长度必须可控。
- JSON API 请求与响应必须有可验证 Schema，并纳入 OpenAPI 总契约；破坏性变更必须版本化或兼容迁移。
- 成功响应业务载荷使用 `data`；错误响应只包含 `code`、`message`、`status`。

## 数据库
- 表和字段命名风格必须统一；数据库默认使用 snake_case；时间字段默认 `created_at`、`updated_at`；布尔字段使用 `is_`、`has_`、`can_` 语义。
- 每张业务表必须有稳定主键、创建时间、更新时间；结构变更必须通过可追踪迁移完成。
- 每个字段必须有详细描述、约束、注意、关联、依赖、单位、国际标准依据、隐私与迁移说明。
- 金额不得使用浮点类型；精度、范围和溢出策略必须明确；单位优先使用 ISO 8601/RFC 3339、ISO 3166、ISO 639、ISO 4217、ITU-T E.164 等标准。
- 索引必须记录用途、字段顺序、选择性和查询场景；默认使用 `pk_`、`uk_`、`idx_` 前缀；迁移可创建、验证和回滚；禁止无依据堆叠索引。
- 多租户仅在蓝图确认有此需求时启用。生产网关从已验证 JWT Claim 提取 `tenant_id` 并注入下游 query；服务不解析 JWT、不感知网关；多租户表和查询遵守租户边界。

## 工程结构与领域对应
- 一个产品可包含独立 frontend 和 backend 工程；每个工程内部一级按业务领域组织 `modules`，领域内部再按技术职责划分。
- 使用 `module-map.yaml` 建立前后端、数据库、API、事件和依赖的一一对应；每个模块必须有职责描述、包含范围、排除范围和依赖边界。
- 需求、领域、API、数据库、事件、前端、后端和测试使用稳定编号并可追踪。

## 配置
- 配置覆盖优先级必须为：环境变量 > 配置文件 > 硬编码默认值。
- 同一项目中环境变量名称和值的业务语义必须统一；各语言和框架使用原生配置机制读取和覆盖环境变量。
- 硬编码只能提供默认值，不得覆盖配置文件或环境变量；配置文件不得覆盖环境变量；生效方式遵循框架原生能力。

## 错误码与安全
- `status` 使用分类前缀：`SYS_`、`COMMON_`、`AUTH_`、`{MODULE}_`、`EXT_`、`DATA_`、`INTEGRATION_`；错误码登记模块、HTTP code、可重试性、客户端动作、版本和废弃状态；错误码不可复用。
- 生产安全模型为 `gateway-enforced-trust-boundary`：服务部署内网，互联网不能直达；网关负责认证、授权、限流和外部安全，服务代码对网关无感知。
- 服务仍必须校验业务数据和业务规则；不得在服务中重复实现网关 JWT 认证授权。

## 交付
- 蓝图和契约先于实现；破坏性变更必须版本化；需求—设计—实现—测试必须可追踪；国际性数据使用国际标准；新需求和规范必须同步更新蓝图。
